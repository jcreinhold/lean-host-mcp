## Fixed completion criteria

These criteria remain fixed through any implementation. Completion requires evidence for every item; missing or failed coverage stays open and is never renamed a pass.

1. A durable, externally retained attempt ID and recoverable complete intent/source binding exist before the execution helper is spawned or begins admission. Lost/partial first replies do not lose that handle.
2. Honest phase-specific evidence separates preparation, target authorization, actual target launch, semantic result, helper custody release, descendant-group closure and actual reap. Unknown stays unknown where a witness is absent. No historical outcome rewriting.
3. The existing native owners retain locks, descriptors and actual-child/group ownership through closure. Journal records never grant custody or replace those owners.
4. Confirmed closure permits ordinary successor progress through normal admission when current intent storage and other native resources are available, even if an earlier result/receipt publication failed. A genuinely unavailable/full journal can still refuse a NEW intent explicitly; this is distinct from an old unknown row retaining released custody. Missing evidence does not create a stopped-work SQL/evidence hold; live or uncertain native custody is never bypassed.
5. The complete normal production workflow works: readiness/preparation, guarded compilation, metadata reads, axioms, importing consumer, lint, semantic checks, actual compatibility and final complete-input validation. Existing proof/axiom/source gates are preserved.
6. Independent adversarial design and code review challenges producer authentication, ordering, aliases, simultaneous owner loss, retention and coverage. Findings must be resolved or explicitly block completion.
7. Real-process fault injection on the exact frozen release binary covers every lifecycle boundary below. Record source/dependency/lockfile revisions, binary hashes, injected fault, causal trigger, actual oracle, passed/failed/skipped/not-run coverage and residual limits. Unit/model tests do not substitute for missing exact-image cases.
8. Only after review and qualification: separately authorized safe maintenance deployment of the tested matched image, followed by production verification of version/hash/behavior and one newly scoped normal workflow. No deployment is authorized now. Proof lanes may continue under the installed stack.

The currently relevant Mac backend pins the actual unreaped leader while checking the complete inherited group. The Linux backend is weaker after leader reap and cannot safely signal a surviving/late-forked descendant from stale identity; do not claim Mac qualification establishes Linux behavior. Deliberate detach/regroup, canonical-inode replacement and undeclared writes remain outside the supported custody contract. No claim of exactly-once arbitrary Lean/Lake I/O across different attempts is added.

Completion does not require impossible historical reconstruction or every crash yielding a known result. It requires the documented unknown cases, safe native exclusion and independent future progress, without false success or hidden replay.

That scanner expects generation directories with owner records and rejects arbitrary foreign files. The native evidence namespace may be a private sibling of the configured native ownership registry; final path and API are not yet selected.

A concrete SQLite layout under consideration is immutable `attempts` (full intent bytes/digest), exclusive `helper_claims`, append-only `observations` keyed by attempt/stage/kind/producer, and `store_meta` incarnation/high-water sequence. There are no pending-job, worker-lease or source-lock tables. The file alternative represents the same objects as a manifest, exclusive claim, immutable observation files and durable allocator metadata. Neither schema/layout is approved yet.

SQLite is a plausible simplification for concurrent create/claim/append/expiry, not a decision already made. Files remain a valid alternative only if their equivalent durability and race-handling cost is demonstrably smaller. Do not implement both backends merely to postpone the choice.

SQLite's transaction guarantees still depend on the VFS/filesystem and flush assumptions. Its documented synchronous modes distinguish rollback EXTRA from WAL FULL; NORMAL is not equivalent power-loss durability. [Atomic commit](https://sqlite.org/atomiccommit.html), [synchronous settings](https://sqlite.org/pragma.html#pragma_synchronous). WAL requires same-host cooperation, has one writer and checkpoint constraints; any selected SQLite version must include the documented WAL-reset fix if WAL is used. [SQLite WAL documentation](https://sqlite.org/wal.html).

The proposed boundary is one Rust facade used directly by host/SDK, with a thin versioned one-shot `native-lifecycle create/get/record-helper-wait` CLI in host `src/cli/native_lifecycle.rs` for Python. `create` is storage preparation only; `get` is read-only and never initializes/migrates. `record-helper-wait` is restricted to the creator's actual-child wait sink and bound helper identity, not arbitrary stage/closure JSON. No extra running service is required. A Python native-library binding remains an alternative only if measured simpler; it must expose the same facade, not a second SQL implementation. Generic source binding is opaque to the server; it stores/returns exact bytes, not Proofs-specific table keys. A lost create reply has a durable caller creation key/original-handle lookup and cannot trigger helper spawn until the original allocation is recovered. A new create API alone allocates; GET never creates or dispatches.

## Identity, evidence and authentication

A handle binds store incarnation, a never-reused creation sequence (or an equally reviewed nonreuse mechanism), unpredictable nonce, role and immutable intent digest. Complete original source/configuration/tooling binding is retrievable inline or by a durably retained immutable-object reference; a digest with lost bytes does not fix the30a failure. The existing `NativeProcessIdentity` contains version/PID/kernel birth/session/PGID only. Configured executable identity and the actual parent relationship are separate bound observations, not fields it already supplies. A saved PID/path is never authority to signal. Cross-language launch binding must encode raw Unix argv/environment/path bytes unambiguously (for example length-prefixed bytes), not lossy UTF-8. Before coding, specify whether the environment digest covers the complete effective inherited environment or supplied overrides plus declared inheritance; these are not interchangeable. Decide which original values versus digests are retained and claim recoverability only for retained bytes.

Writer H exclusively claims an unexpired, existing prepared attempt before admission. Readiness comes from the exact accepted B/guardian lifetime, bound to attempt, command argv/environment/cwd (preserve raw Unix bytes), staged stdin digest/count and native owner. A caller-provided JSON claim alone is not authenticated native evidence. The proposed producer contract uses the accepted native private-channel/generation identity for native Ready/GO/closure facts, and a separate role-bound creator capability for the source-reviewed controller actual-child wait sink. A native CLI receiving wait JSON does NOT independently verify a kernel wait: label that fact `controller_reported_actual_wait`, while a Rust owner recording its own successful `Child::wait` is `native_observed_actual_wait`. Only the trusted actual-Popen sink may invoke the restricted wait publication, after its wait succeeds; journal access must also match original creator PID/birth and the exclusively claimed helper identity. Wrong capability, role, helper or controller identity refuses. Raw PID/exit-code JSON from another caller cannot mint native-observed wait evidence. Exact capability transport/parent-identity capture and rejection fixtures still require review before coding. Payloads receive no journal mutation or GO capabilities. Protect against stale/wrong attempt, owner, source, command, input, namespace and restored-store identities.

Threat scope remains cooperating trusted local code and a stable private namespace. Same-UID malicious code that can replace the executable, mutate all private files or deliberately escape the group contract is not magically excluded by a nonce, SQLite or JSON signature. This limitation must be stated instead of claiming stronger authentication than the implementation provides.

A top-level operation has one external attempt before its first execution helper; custody-bearing helper children use explicit child-role scopes and actual identities linked to that intent; allocate additional child attempt IDs only if demonstrably needed. Existing SDK generation IDs bind B/G; descendants are closed by the existing whole-PGID contract, not a new per-PID registry. Journal/discovery CLI processes perform no workload admission and are not recursive execution helpers. Metadata proxy/transfer roles must be represented explicitly when used, rather than hidden as an unstarted proof payload.

Immutable intent + append-only facts are sufficient; mutable aggregate status is a computed view, not a replay or capacity policy. Minimum separate facts: intent durable; helper claimed; preparation/admission progress; wrapper created; possible GO; target spawn/exec witness if available; target result; owned-group closed; helper-owned aliases released; actual helper/child reaped; evidence expired/unavailable. Store full producer identity and scope on each fact. Conflicting/forged/reused facts refuse; they cannot overwrite earlier observations.

## Ordering and protocol boundaries

1. **Creation:** synchronously persist full intent and durable handle before spawning H. Failure refuses before spawn. Persist a caller-side handle/reference before first reply can be lost. A helper that exists without a successful native identity claim cannot enter admission/accept a stage.
2. **Admission:** H records its exact identity before waiting; planned domains differ from actually held locks/loans. Acquired custody and helper asset directory are recorded before the initial successful reply. Loss of that reply preserves handle and unavailable result; it does not silently create another helper.
3. **Writer stage:** record the full stage command and index before blocked wrapper creation. Persist actual wrapper/group identity under all canonical lock domains before GO as today. Durably record possible GO before the first attempted launch byte. A journal/FS commit cannot be atomic with pipe delivery; a crash in this gap is deliberately uncertain, never NoDispatch. Partial GO without a stronger sealed child witness stays unknown even when a test counter happens to be zero.
4. **Reader stage:** the existing guardian ACK permits preparation/read admission only. After complete read union, retained guardian-loan ACK and validated staged input, B publishes authenticated Ready. H may release one private stdin GO only while original deadline/caller/cancellation permit it, after possible-GO persistence. P is spawned once. Readiness or missing GO rows alone do not prove NoDispatch while any sender can still grant GO.
5. **Negative dispatch:** first irrevocably seal/take/drop the GO sender (or receive bound child NoGO after its receiver is sealed). Transfer only stop/reap capability to cleanup. Then publish scoped target-not-dispatched independently of uncertain preparation/custody. Any GO attempt or missing seal witness remains unknown unless stronger bound target evidence exists. Startup ACK, generation0, empty output/domains and retryable flags are insufficient. H alone owns the one-shot sender and an irreversible AwaitingReady -> PossibleGO OR SealedNoGO decision; persistence ambiguity stays on the PossibleGO/unknown side. Cleanup receives only stop/reap capability. Child receiver-sealed NoGO is separately authenticated stronger evidence, not a second sender. Distinct per-kind files alone cannot prevent contradictory cross-process claims; backend/API and runtime ownership must enforce the producer/state rule.
6. **Result:** actual target spawn, target wait/output, stopped group and semantic verdict remain separate. A writer started frame is not final exec proof; helper/wrapper exit0 is not proof success. Preserve all existing negative Lean verdicts and unavailable results.
7. **Closure:** seal further dispatch, wait/retain actual group and inherited-FD barrier, then record stopped group before wire reply. Explicitly drop every declared owned lock/demand alias before claiming helper-scoped custody release. Borrowed originals are presently left open by SDK duplication; duplicate File drop is insufficient. Caller/other-process aliases are never covered. Actual H reap closes H's table but does not establish surviving descendant-group closure.
8. **Late reap / progress:** existing actual-child wait owners publish a bound successful actual wait, including after bounded caller return. Wait authority errors or persistence failure stay unknown. The journal never holds OS resources after their real closure solely to save a receipt; ordinary native successor admission depends on existing locks/groups, not a stale journal row. Conversely missing receipts never bypass a live fence. Cleanup continues through the existing owner/lifeline after transport loss; no new recovery daemon.
9. **Owner loss:** controller EOF requests stop; H/G loss uses existing inherited locks and previous-group/reader fences. Simultaneous controller/helper loss may lose all terminal publishers; simultaneous native-reader H/G loss with a surviving target or FD-closing descendant is a separate adversarial case, not covered by killing only Python/H while G survives. Record unknown/unavailable; do not infer old closure from absent PIDs, later success or current idle state. No new storage can recover an event never durably witnessed.

## Lookup, restart and bounded retention

Read-only lookup has explicit byte/page/time limits as well as stored row/file/stage limits. A bounded cursor is tied to the original attempt and a consistent observation view/version; partial/truncated output is labelled incomplete, never accepted as complete input or closure. Retain/retrieve the complete original intent via bounded pages/object references without an unbounded all-history response. Numeric response/page caps and concurrent late-observation paging remain implementation decisions.

Read-only lookup requires the original handle; it returns exact immutable intent plus independent evidence and explicit unavailable/expired/corrupt states. It never opens a new attempt, submits work, signals stored PIDs, ACKs a semantic request, clears a lock or rewrites original results. Server restart reopens the native store with the same incarnation; current native OS custody/fences independently decide new admission. Missing historic data remains unknown. Controlled restore/import is separately authorized quiescent journal maintenance: fence creation and publishers, mint and durably commit a new incarnation BEFORE enabling writes, preserve old handles as read-only history, and never roll the creation sequence backward into reused IDs. Neither SQLite nor files detect an arbitrary unmanaged whole-store rollback; that rollback is outside the contract and cannot be silently opened as a writable restored store.

Retention is observational, not custody. The earlier suggestion to keep every unresolved observation forever under a finite global count is rejected: permanently missing witnesses would eventually create another permanent hold. Advertise a finite evidence-retention promise and bounds on attempts, stage facts and bytes. Exact numeric defaults are undecided and must be justified without changing current native capacity/deadlines. Within the promised window, exhaustion gives explicit bounded pre-spawn storage failure. At expiry, even unknown evidence may become unavailable/unknown; expiry never means stopped, successful or replayable.

Only create() allocates a new never-reused ID. Claim/open/get require an existing exact unexpired attempt; late append updates only an existing matching attempt, never UPSERTs or recreates an evicted directory. No new helper claim or possible-GO authorization may commit after expiry. A GO authorized before expiry may still be in flight or execute afterward; storage expiry cannot atomically revoke pipe delivery or prove cancellation. The original deadline/cancel checks still apply at each gate. Already-running work retains normal native cleanup and may lose publication. Publishers and GC must have a defined atomic order; no resurrection. No unbounded tombstones are needed if store-incarnation + durable high-water sequence prevent reuse, including restore. Exact max-age, active-publication behavior, storage-outage handling and schema migration are review decisions still open, not implemented settings.
